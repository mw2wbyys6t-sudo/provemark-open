# 数据与数据库手册（Data）

目标：**数据不丢、查询不慢、变更不停机**。

## 1. Schema 设计

- 先建模再建表：实体、关系、基数、生命周期；
- 范式化优先（避免更新异常）；只在有实测读放大时反范式，并写明同步方式；
- 每张表有明确主键（自增 ID 与业务唯一键分开）；时间字段统一时区（推荐 UTC 存储）；
- 金额用整数分或 `DECIMAL`，不用 float；
- 软删除要评估：唯一索引、查询过滤、数据增长、合规删除怎么处理；
- 命名统一、字段可空性显式；枚举值写进约束或字典表。

## 2. 索引与查询

- 索引服务于**具体查询**：按 WHERE/JOIN/ORDER BY 的列组合建；
- 复合索引注意最左前缀；区分度低的列放后面；
- 避免在索引列上做函数/隐式转换（如 `WHERE date(created_at) = ...`）；
- `LIKE '%x'` 走不了普通索引；需要全文/前缀索引/搜索引擎；
- 分页：深 offset 会越翻越慢，改用 **keyset（游标）分页**；
- 用 `EXPLAIN`/执行计划验证，不靠猜；慢查询日志设阈值并定期看。

## 3. 事务与锁

- 事务保持短小：不在事务里做 HTTP/文件/长计算；
- 明确隔离级别与影响；读已提交下的“先查后写”不是原子操作；
- 死锁：固定加锁顺序、缩小范围、捕获后有限重试；
- 批量更新分批提交，避免长事务与锁等待；
- 乐观锁（版本号）适合低冲突；悲观锁适合高冲突但会降并发。

## 4. 迁移（Migrate）

- 所有 schema 变更走版本化迁移，禁止生产手工改表；
- **expand → migrate → contract**：先加新列/表并双写，再回填，切读，最后删旧；
- 迁移要能在旧代码运行时执行（发布顺序兼容）；大表回填分批、可暂停；
- 每个迁移有回滚或至少“前进修复”方案；上线前在接近生产的数据量上演练；
- 不要在生产开 ORM 自动同步（`AI-018`）。

## 5. 备份与恢复

- 备份要定期**演练恢复**，没恢复过的备份等于没有；
- 明确 RPO（能丢多少数据）与 RTO（多久恢复）；
- 逻辑备份 + 物理备份结合；备份加密、异地保存、权限最小化；
- 删除/脱敏流程可审计（合规要求时）。

## 6. 数据质量与一致性

- 关键表加 NOT NULL/唯一约束/外键（或应用层强校验 + 对账）；
- 双写/异步同步要有对账任务与修复脚本；
- 数据管道：幂等写入、去重、迟到数据处理、schema 演进；
- 定期统计（空值率、分布、异常值），数据异常先当 bug 查。

## 7. 容量与性能

- 估算增长：行数 × 行宽 × 索引数 × 副本数；
- 大表归档/分区/冷热分离；TTL 清理；
- 连接池：大小、超时、泄漏检测；池耗尽通常是慢查询或未释放；
- 缓存只缓存可重建的数据（见 `architecture-playbook.md` §4）。

## 8. 边界

- 手册是通用判据；具体数据库（PG/MySQL/SQLite/Redis）以官方文档为准；
- 没有执行计划的“优化”都是猜测；
- 生产变更的风险主要在**迁移与回滚**，不在 SQL 语法。
