# 维护纪律：让 AI 不把项目越改越糟

这套能力的核心不是"把仓库扫成 0 分"，而是**防止在维护一个本来就有问题的项目时，越改越糟**。

AI 参与维护时，"越写越有问题"通常是四种机制叠加：

1. **范围漂移**：修一个问题顺手动 8 个文件，顺手重构、改格式，回归面扩大；
2. **修 A 引 B**：把 SQL 拼接改成字符串模板，注入没了，模板注入来了；
3. **噪声淹没**：一次报告 40 条，模型全想修，改到第 3 条就忘了第 1 条的前提；
4. **用 suppress 掩盖**：新增问题用一条新的 `ignore` 消掉，看起来"修好了"。

对应四条机制，插件提供四个约束：**范围纪律 + 每次复核 + 基线与趋势 + 禁止掩盖回归**。

## 1. 基线与趋势（棘轮）

- **第一次**扫描某个工作区时，抓一份基线快照（分数、各严重度计数、全部 finding 指纹），并**持久化**到
  `~/.dsh/provemark-dsh/baselines.json`（`PROVEMARK_DSH_BASELINE_FILE` 可覆盖；`persistBaseline: false` 关闭）；
- 之后每次扫描（后台或工具）都与基线比较，得到：
  - `trend`：一句话，例如 `⛔ 较跨会话基线 97 分变差：新增 2 条问题（VUL-001(a.py)、…）`
  - `newFindings` / `fixedFindings`：新增与修掉的条数
  - `baselineScore`：基线分数
- **重启宿主不会重置棘轮**：跨会话比较时文案写「跨会话基线」；确认要接受当前状态时用 `provemark_guard(resetBaseline: true)` 重置。
- 判定联动：新增里出现 critical/high → `verdict = blocking`；只有中低 → 至少 `warn`。
- 状态块里也会出现同一句 `trend`，所以模型在写最终答复**之前**就能看到"这次改动让项目变差了"。

**老项目基线差是允许的**：基线记录的是"进来时的样子"，只要求"不比进来时更差"。这就是棘轮的语义。

## 2. 大仓库维护协议（照做就不会失控）

1. **先跑一次全量扫描**，拿到基线与完整清单（`provemark_guard` 或 `scan -f json`）；
2. **按严重度/CWE 取一批，最多 3–5 条**：先 critical/high（注入、校验关闭、真实密钥），再 medium；
3. **只改与这批相关的文件**：不做顺手重构、重命名、批量格式化；
4. **每改完一批就复核**：`provemark_guard(fresh: true)`，看 `trend`；
5. **新增必须为 0**：`newFindings > 0` 就回退或先修这批新增，再继续下一批；
6. **剩余问题**：要么登记带原因与到期日的 `[[ignore]]`（只用于已确认的历史问题），要么写进待办；不要"一次性清空"；
7. **交付前**：`blocking = 0`，或明确说明"还剩什么、为什么现在不修、谁在什么时候修"。

## 3. 反模式清单（看到就要停）

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一口气修 20 条 | 回归面太大，review 不了 | 一批 3–5 条，逐批复核 |
| 顺手重构/重命名/格式化 | diff 淹没真实修复 | 修复 PR 只含修复 |
| 用新 `[[ignore]]` 消掉新增问题 | 棘轮失效，退化被掩盖 | ignore 只用于已确认历史问题 |
| 先改代码再看报告 | 不知道改之前是什么样 | 先扫描拿基线，再改 |
| 把 `--offline` 当默认求快 | 漏洞/许可证未验证，误判"很健康" | 默认联网；断网时看 `reliable` 与 notes |
| 拿局部扫描（`only`）当整仓结论 | 分数失真 | 局部扫描只作定位，结论用全量 |

## 4. 和门禁/CI 的关系

- 本地：`provemark_guard` 的 `trend` 是"这轮有没有变差"的即时读数；
- 提交前：`scan --staged --fail-on high` 阻止新问题进历史；
- CI：`scan --fail-on high -f sarif` + SARIF 上传，把新增问题落到行级；
- 历史遗留：用 `[[ignore]]`（必须写原因 + 到期日）建立可审计的豁免，而不是放宽门禁。

## 5. 边界（诚实）

- **基线持久化有上限**：最多 50 个工作区、每个最多 500 条指纹；删掉缓存文件或 `resetBaseline` 会重新开始，
  长期审计仍应看 CI 侧的 SARIF/报告存档；
- **不做数据流分析**：`trend` 说明"问题变多/变少"，不判断"这行输入是否真的可控"；
- **不阻止用户手动改坏**：仓库被编辑器改坏时，下一次扫描同样会体现在 `newFindings` 里——这是特性，不是缺陷。
