# 全栈工程手册（判据 · 清单 · 反模式）

安全规则（`VUL-*`）管“会不会被打”，这份手册管“**能不能长期跑、改起来会不会散架**”。
规则能给的是信号，手册给的是判断和动作。

## 1. 分层检查清单

### 前端（浏览器）
- 状态：服务端状态与 UI 状态分开；请求要能取消（`AbortController`）、失败要有重试/降级，不能只写 happy path。
- 渲染：列表要有 key 且不用数组下标；`dangerouslySetInnerHTML` / `v-html` 只接清洗过的内容。
- 性能：首屏体积、路由级拆包、图片尺寸与懒加载；避免在 render 里做重计算。
- 可访问性：语义标签、`label` 绑定、键盘可达、对比度；表单错误要能被读屏读到。
- 边界：空态、加载态、错误态、超长文本、离线、慢网——AI 通常只写成功态。

### 后端（服务/API）
- **契约先行**：方法、路径、状态码、错误体（统一 `{code, message, details}`）、分页（`cursor`/`page`+`limit`）、版本策略。
- **幂等**：创建/支付/消息消费要有幂等键；重试不产生重复副作用。
- **超时**：任何外部调用（DB/HTTP/队列）都要有超时；重试要有限次 + 指数退避，非幂等写不重试。
- **错误处理**：区分可重试与不可重试；不要把异常吞成 200；日志带 request id。
- **认证/授权**：认证在网关/中间件统一做；授权在每个资源访问点校验（别只在前端隐藏按钮）。
- **输入校验**：schema 校验（pydantic/zod）+ 长度/范围；不要信任客户端传来的 id、价格、角色。

### 数据库
- schema 变更走**迁移**，生产不开 `synchronize`/`dropSchema`；迁移要可回滚或至少可前进。
- 索引：按查询条件建；注意最左前缀；`LIKE '%x'` 走不了索引。
- 事务：保持短小，不在事务里做网络调用；注意隔离级别与死锁重试。
- 查询：列表必须分页；避免 N+1（批量 `IN`、`selectinload`/`populate`/`include`）；避免 `SELECT *` 进大表。
- 连接池：池大小与超时显式配置；慢查询要有日志/阈值。

### 异步与并发
- 循环里 `await` 是串行：能并发用 `asyncio.gather` / `Promise.all`，但要限制并发数、单个失败不能拖垮整批。
- 共享可变状态要加锁或用原子操作；不要“先查再写”当原子（用唯一约束/乐观锁）。
- 后台任务要有重试、死信、幂等；不要让请求线程等长任务。

### 部署与运行
- 12-Factor：配置走环境变量；日志走 stdout；无状态进程；优雅停机。
- 容器：固定镜像 tag/digest、非 root、健康检查；不挂 `docker.sock`。
- CI：锁文件安装（`npm ci` / `uv sync --locked`）、固定 Action SHA、最小权限 `permissions`。
- 可观测性：结构化日志 + 指标（延迟/错误率/饱和度）+ 追踪（request id 串起来）；定义 SLI/SLO 与告警阈值。
- 发布：灰度/回滚预案；数据库迁移与代码发布顺序要兼容（先加后删）。

### 测试
- 分层：单元（纯逻辑）→ 集成（DB/HTTP 边界）→ 端到端（关键路径）；不要只测 happy path。
- 改行为必须补测试；bug 修复先写复现用例。
- 测试要可重复：固定时间、随机种子、外部依赖用契约替身。

## 2. AI 生成代码的高频工程反模式

| 症状 | 后果 | 修法 | 规则 |
| --- | --- | --- | --- |
| `requests.get(url)` / `fetch(url)` 没有超时 | 对端挂起拖垮线程/连接池 | 超时 + 有限重试 + 退避 | AI-015 |
| 循环里逐个 `await` | 延迟线性累加，吞吐塌陷 | 并发（限流）或批量 | AI-016 |
| 循环里逐条查库 | N+1，数据量一大就崩 | 一次批量取 / 预加载 | AI-017 |
| TypeORM `synchronize: true` | 启动即改库，可能丢数据 | 迁移管理 schema | AI-018 |
| `ALLOWED_HOSTS=['*']` / CORS 全开 | 任意站点可带凭据调用 | 显式域名白名单 | AI-019 |
| `print` / `console.log` 当日志 | 无级别/无上下文/无法关闭 | 结构化日志 | AI-020 |
| 只写 happy path | 空态/错误态/慢网直接崩 | 补边界与错误分支 | — |
| 一次性大改 | 回归面失控，review 不了 | 分批、每批复核 | 维护纪律 |

## 3. 性能与可观测性判据

- **先测量再优化**：没有 p50/p95/p99 与错误率数据，不做“优化”。
- **瓶颈三选一**：CPU、IO（DB/HTTP/磁盘）、锁/串行化；先定位再改。
- **缓存**：只缓存“可重建、可过期”的数据；写路径要处理缓存失效；防击穿（单飞/互斥）。
- **日志**：结构化（JSON）、级别、request id、耗时；不要打印 PII/密钥；采样高流量路径。
- **指标**：RED（Rate/Errors/Duration）或 USE（Utilization/Saturation/Errors）；告警要可行动。

## 4. 与插件配合的用法

1. 写代码前：读本手册的清单，按任务范围挑 1–2 条硬约束；
2. 写代码时：常驻提示词里的“工程常识”会提醒超时/幂等/迁移/日志/测试；
3. 改完：`provemark_guard` 看 `AI-015~020` 是否命中、`trend` 有没有新增；
4. 大项目：先按严重度分批（安全 → 工程 → 规范），每批修完复核，新增为 0 再继续；
5. 交付：`blocking=0` 或说明剩余项与原因。

## 5. 边界

- 规则只覆盖**能在源码里稳定识别**的模式；架构合理性、领域建模、容量规划仍需人判断；
- 本手册是通用工程判据，不是某个框架的最佳实践全集；具体框架以官方文档为准；
- 没有“全部知识”这种东西：遇到手册没覆盖的问题，先测、再读文档、再决定，别让模型凭空发明 API。
