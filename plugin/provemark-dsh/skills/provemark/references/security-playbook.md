# 安全实战手册（代码级）

这是 `VUL-*` 规则背后的知识整合：**怎么判、先修什么、常见修法是什么、哪些是工具的边界**。
规则给出"哪里有问题"，这份手册给出"接下来怎么做"。

## 1. 判定顺序（先看什么）

拿到一组 VUL finding 时，按这个顺序处理，不要按文件顺序：

1. **能否直接控制服务器/数据**：命令注入（VUL-002）、反序列化（VUL-004）、SQL 注入（VUL-001）、SSTI（VUL-003）、XXE（VUL-015）→ 立刻修；
2. **能否绕过认证/加密**：JWT 校验关闭（VUL-012）、TLS 校验关闭（VUL-010）、弱哈希用于口令（VUL-008 high）；
3. **能否读/写不该碰的文件或网络**：路径穿越（VUL-006）、SSRF（VUL-007）；
4. **前端/浏览器面**：未转义 HTML（VUL-005）、Cookie 安全属性（VUL-013）；
5. **配置类**：调试模式（VUL-014）、容器提权（VUL-018）、Actions 脚本注入（VUL-017）。

判断"能不能被触发"只需回答三个问题：**输入从哪来**（用户/上游/配置）、**有没有校验**（类型、白名单、长度）、**权限边界在哪**（进程/容器/账号）。三者都弱 → 就是真实可利用。

## 3. 每类问题的“标准修法”

- **SQL 注入**：参数化查询（`?` / `%s` 占位符 + 参数列表）；动态表名/列名走白名单映射，不拼接。
- **命令注入**：参数列表执行（`subprocess.run([...])`、`execFile`），不经过 shell；必须拼接时白名单校验每个参数。
- **模板注入**：模板源码只能来自代码/文件；用户输入作为变量传入，绝不拼进模板文本。
- **反序列化**：外部数据只用 JSON；必须兼容旧格式时加 HMAC 签名并校验来源。
- **XSS**：默认转义；富文本用白名单清洗（bleach / DOMPurify）；禁用 `Markup` / `|safe` / `innerHTML` 直接放行用户内容。
- **路径穿越**：固定根目录 + `resolve()` 后校验仍在根内；文件名白名单；不信任客户端文件名。
- **SSRF**：目标域名/IP 白名单；解析后拒绝私网、回环、链路本地（169.254.169.254）；不跟随跨域重定向。
- **弱哈希**：口令用 bcrypt / argon2 / scrypt；完整性用 SHA-256 / BLAKE2。
- **弱随机**：令牌/盐/会话 ID 用 `secrets` / `crypto.randomBytes`。
- **TLS**：保持校验；自签证书把 CA 加信任库，不改 `verify=False`。
- **JWT**：固定算法、校验签名 + `iss` + `aud` + `exp`；不信任头部 `alg`。
- **XXE**：`defusedxml`，或 `resolve_entities=False, no_network=True`。
- **调试模式**：生产默认关闭，由环境变量控制；Werkzeug console 等于 RCE。
- **Actions 注入**：事件字段经 `env:` 传入并用引号包裹，或改用 `github-script`；不要直接插值进 `run:`。
- **容器**：去掉 `privileged`；按需 `cap_add`；不挂 `docker.sock`。
- **C 内存函数**：`snprintf` / `strncpy_s` / `fgets` + 边界检查；开启编译器加固。

## 4. 工具边界（什么时候别信它）

- **只覆盖源码里看得见的模式**：运行时配置、WAF、依赖链、业务逻辑（越权、竞态、事务）不在内；
- **不理解数据流**：`requests.get(url)` 里 `url` 是否用户可控需要人判断；规则只能看到"像是从请求里来"；
- **注释/文档字符串不报**：文档里的示例代码不是漏洞；
- **测试代码降级**：`tests/**`、`*_test.go` 命中置信度 ≤0.5，只作提示；
- **误报处理**：确认是误报后登记带原因与到期日的 `[[ignore]]`，不要长期静默；
- **别把"没报"当成"没漏洞"**：AI 生成代码的漏洞常常需要结合业务语义判断，规则是下限不是上限。

## 5. 和整体流程的关系

1. 写代码时：提示词里的红线覆盖同一批类别（注入/密钥/反序列化/TLS/PII/供应链）；
2. 提交前：`provemark_guard` 给出 `blocking` 判定（有 critical/high 即阻断）；
3. 修复：业务代码按本手册改；配置类可用 `autoFix: apply` 补安全文件；
4. 出报告：`provemark_scan` 的 `detail.cwe` / `detail.owasp` 直接进整改单与 SARIF；
5. 长期：`[[ignore]]` 必须写原因和到期日，过期会重新计分。
