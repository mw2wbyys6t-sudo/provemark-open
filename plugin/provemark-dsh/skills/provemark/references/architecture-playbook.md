# 架构手册（Architecture）

目标：让系统**改得动、坏得小、扩得开**。判断标准不是“先进”，而是“变更成本”。

## 1. 边界与依赖

- 按**变化原因**拆模块，不按技术分层硬拆；一个模块只对一类变化负责；
- 依赖方向单向：业务 → 领域 → 基础设施；反向依赖用接口反转；
- 跨模块只通过明确契约（函数/HTTP/消息），不共享内部数据结构；
- 循环依赖是设计红灯：要么合并，要么抽公共层；
- 第三方 SDK 包一层适配器，避免全仓被某个库的 API 绑死。

## 2. 数据归属

- **每份数据只有一个写入方**（single writer）；其他模块读副本或调接口；
- 跨模块事务尽量不做；必须一致时用：
  - 本地事务 + **outbox**（同库事务写事件表，异步投递）；
  - **saga**（补偿事务，每步可逆）；
  - **幂等 + 重试**（至少一次投递，消费端去重）；
- 状态机显式化：合法状态与转移写在代码里，别靠约定。

## 3. 同步 vs 异步

| 场景 | 选择 |
| --- | --- |
| 用户等待结果、强一致 | 同步调用 + 超时 + 有限重试 |
| 可延迟、可重试、削峰 | 消息队列 + 消费者幂等 |
| 跨服务长流程 | 编排（saga/工作流）而非链式同步调用 |
| 通知类 | 事件 + 失败告警，不阻塞主流程 |

异步的代价：最终一致、重复投递、顺序问题、可观测性更差。没有这些准备就别上。

## 4. 缓存

- 只缓存**可重建、可过期**的数据；先问“脏了会怎样”；
- 缓存 key 带版本/租户，避免串数据；
- 失效策略：TTL 兜底 + 写路径主动失效；
- 防击穿：单飞（single-flight）/互斥重建；防雪崩：TTL 抖动；
- 热点大 key 拆分；缓存与库不一致要有对账/修复路径。

## 5. 一致性与并发

- 读多写少：读写分离 + 延迟容忍；写后读要读主库或加版本号；
- 并发更新：乐观锁（版本号）/悲观锁（行锁），按冲突概率选；
- 幂等键：客户端请求 id / 业务唯一键，落库唯一约束兜底；
- 分布式锁只用于“减少重复”，不能当正确性保证（要有兜底约束）。

## 6. 伸缩与故障隔离

- 无状态服务易扩；有状态（会话/缓存/队列）外置；
- 限流/熔断/隔离舱：慢依赖不能拖垮全站；
- 超时预算：入口超时 ≥ 下游超时之和 + 余量；重试要算进预算；
- 关键路径降级方案（返回缓存/默认值/排队），并明确降级可接受性。

## 7. 接口演进

- 加字段向后兼容；删/改字段走“先加新、双写、切读、再删旧”；
- 版本策略：URL 版本或媒体类型版本，明确兼容窗口；
- 错误码稳定；分页/排序/过滤语义写进契约；
- 契约测试/OpenAPI 校验进 CI。

## 8. 什么时候不要微服务

- 团队小、边界不清、没有独立伸缩需求时，模块化单体更便宜；
- 拆服务的真实成本：网络故障、分布式事务、可观测性、部署编排；
- 先模块化（清晰边界），等到**独立变化/独立伸缩**成为瓶颈再拆。

## 9. 架构决策记录（ADR）模板

- 标题：决策一句话
- 背景：约束与目标（性能/成本/团队/合规）
- 选项：至少两个，含“不做什么”
- 决定与理由
- 后果：正面/负面/需要后续跟进
- 状态：提议/已采纳/已废弃

## 10. 边界

- 架构不是一次性设计：随证据演进，别过度设计；
- 手册给的是判据，不是标准答案；具体选型看团队与数据；
- 没有容量数据时，“高可用/高并发”都是空话。
