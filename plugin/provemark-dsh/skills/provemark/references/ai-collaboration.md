# 与 AI 协作编码手册（AI Collaboration）

目标：让模型**产出可验证的代码**，而不是“看起来很自信的代码”。这份手册是给使用插件的模型和用模型的人共同看的。

## 1. 任务怎么给

| 给法 | 结果 |
| --- | --- |
| “帮我优化一下这个项目” | 范围失控，回归面巨大 |
| “修 `a.py:42` 的空指针；只改这个函数；补一个复现测试” | 可验证、可回滚 |
| “先读 3 个文件，给出计划，我确认后再改” | 适合陌生/大仓库 |

要点：**目标 + 范围 + 验收标准 + 禁止项**。一次任务只做一件有边界的事。

## 2. 上下文怎么给

- 给**入口文件、关键类型、错误日志、复现命令**，而不是整仓粘贴；
- 大项目先让模型读 `README`/入口/目录结构，再给具体文件；
- 不要给过期快照：改完代码让模型重新读文件，而不是凭记忆；
- 用工具（`provemark_guard`、测试命令）代替“我觉得应该没问题”。

## 3. 验证闭环（最重要）

1. 改之前：跑一次基线（测试/扫描），记录结果；
2. 每改一小步：跑相关测试/扫描，看 `trend`；
3. 交付前：全量测试 + `provemark_guard`（`blocking=0` 或说明原因）；
4. 输出里给出**证据**：命令、退出码、关键输出，而不是“已完成”。

## 4. 模型幻觉的常见形态（评审时重点查）

- 调用不存在的 API/参数/配置项（对照官方文档/类型定义）；
- 声称“测试通过”但没跑（要求贴命令与结果）；
- 用旧版本 API（依赖升级后语义变化）；
- 编造文件路径/行号（让模型重新 read 确认）；
- 只写 happy path，忽略空/错/超时/并发；
- 过度重构：把“修一个 bug”变成“重写模块”。

## 5. 怎么让模型“停下来”

- 明确约束：「不要动无关文件；一轮最多 3 个文件」；
- 明确退出条件：「新增问题为 0 才能继续下一批」；
- 遇到不确定：「不确定就先问，不要猜 API」；
- 大改动分阶段：计划 → 小步改 → 验证 → 下一阶段。

## 6. 提示词模式（可直接用）

```text
目标：<一句话>
范围：只允许改 <文件1>、<文件2>
验收：<测试命令> 通过；provemark_guard 无新增 high/critical
禁止：不改公共接口、不升级依赖、不做格式化
步骤：先读文件 → 给 3 行计划 → 等我确认 → 小步改 → 每步跑验证
```

## 7. 信任边界

- **默认不信任模型的“结论”**，只信任可复现的证据；
- 模型可以读代码，但**不要在给外部模型的内容里放密钥/PII**（脱敏后再贴）；
- 生成的命令先看再执行（尤其 `rm`/`curl | bash`/生产数据库操作）；
- 插件自身遵守：只发包名+版本做漏洞查询，不上传源码（见 `tools.md` 的网络说明）。

## 8. 和 Provemark 的配合

| 阶段 | 用插件做什么 |
| --- | --- |
| 开工前 | `provemark_guard` 拿基线（允许项目本来有问题） |
| 写代码时 | 常驻提示词里的安全/工程/算法红线 |
| 每步之后 | `provemark_guard(fresh: true)` 看 `trend` |
| 交付前 | `blocking=0`；修不动的如实说明 |
| 发布前 | `provemark_scan -f sarif` 进 CI 门禁 |

## 9. 边界

- 手册是协作纪律，不保证模型不犯错；
- 复杂业务语义、性能取舍、合规判断仍要人负责；
- 任何“自动化”都不能替代最终的人工 review。
