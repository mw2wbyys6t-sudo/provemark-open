# 代码评审手册（Code Review）

目标：在合并前用最低成本发现**正确性问题**，而不是把评审变成风格争吵。

## 1. 评审顺序（按代价从高到低）

1. **意图**：这个改动解决什么问题？PR 描述能不能说清楚？说不清就先不评审代码。
2. **正确性**：边界（空/单元素/极值/重复）、错误路径、并发/事务、状态机转移。
3. **安全**：注入、鉴权边界、密钥、反序列化、SSRF、日志里的 PII（对照 `security-playbook.md`）。
4. **测试**：有没有覆盖新行为与回归点？测试是否会在实现坏掉时失败？
5. **性能**：数据量放大 10 倍会怎样？循环里有没有 IO/N+1/拼接（对照 `algorithms-playbook.md`）。
6. **可维护性**：命名、抽象层次、重复、注释是否解释“为什么”。
7. **风格**：最后一分钟看，能交给格式化/ lint 的不要人评。

## 2. Diff 卫生（评审效率的 80%）

| 反模式 | 后果 | 要求 |
| --- | --- | --- |
| 一个 PR 混修复 + 重构 + 格式化 | 无法判断哪部分引入了风险 | 一个 PR 只做一件事 |
| 500+ 行大 diff | 评审变走过场 | 拆成可独立验证的小 PR |
| 顺手重命名/移动文件 | diff 淹没真实改动 | 重构单独 PR，且不改行为 |
| 生成代码/锁文件混入 | 噪音巨大 | 生成物单独提交或标注 |

## 3. AI 生成代码的评审重点

AI 的代码通常“看起来对”，评审要专门查这些：

- **幻觉 API/参数**：调用的函数、配置项、SDK 方法是否真实存在（对照官方文档/类型定义）；
- **过度抽象**：为一个小功能引入多层接口/工厂/泛型；问“少一层会不会更清楚”；
- **只写 happy path**：空态、错误态、超时、重试、并发是否处理；
- **复制粘贴的残留**：示例数据、mock、占位配置、未使用变量；
- **悄悄改变语义**：修 A 时顺手改了默认值/精度/排序稳定性；
- **测试与实现一起写错**：断言只验证了实现细节，不是行为；
- **依赖引入**：新包是否真实存在、许可证是否可接受、是否重复造轮子（对照 `SCP-*`/`LIC-*`）。

## 4. 评论怎么写才有用

- 说**影响**，不说“这样写不好”：「这个循环里每次 `await fetch`，10 个用户就是 10 次串行往返，接口 p95 会翻倍；建议 `Promise.all` 或批量接口」；
- 给**可执行建议** + 代码位置；
- 区分 **must fix / should fix / nit**，避免把 nit 当阻塞；
- 对不确定的用提问：「这个 `except Exception` 会吞掉取消信号吗？」；
- 用规则/手册引用代替个人偏好：`VUL-001`、`AI-017`、`AI-021`。

## 5. 合并前检查清单

- [ ] PR 描述：问题、方案、验证方式、风险与回滚
- [ ] 新增/修改行为都有测试，且测试在坏实现下会失败
- [ ] `provemark_guard` 通过：无新增 critical/high（`trend` 无新增）
- [ ] 迁移可回滚或可前进；兼容旧数据/旧客户端
- [ ] 配置/密钥走环境变量，没有硬编码
- [ ] 日志不打印 PII/凭据；错误可定位
- [ ] 文档/CHANGELOG 更新（对外行为变化时）
- [ ] 回滚预案明确（开关/版本/迁移顺序）

## 6. 边界

- 评审不能替代测试、静态分析与线上监控；
- 大重构的评审质量有限：优先用“小步可验证”的方式推进；
- 风格问题交给工具，人只评审工具判断不了的事。
