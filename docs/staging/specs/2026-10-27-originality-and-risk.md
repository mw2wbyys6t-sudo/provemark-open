# 原创性与风险防护：能力补齐

日期：2026-10-27
范围：Provemark 0.4（在 0.3 的检测算法之上，补"原创性"与"敏感数据"两块）

## 定位

一句话：在代码进入仓库之前，同时回答两个问题。

1. **这个项目是原创且合规的吗**——没有引入会污染自身的许可证、来源可证明、归因完整。
2. **它带着哪些会伤到自己的风险**——凭据、PII、漏洞、供应链、AI 代码隐患。

明确不做：代码相似度查重。它误报极高，且给不出可操作结论。原创性只做**可验证的证据**：许可证、来源、归因、声明。

## 决策

### D1 原创性拆成三层，每层都有可检查的证据

- 引入层：依赖许可证组合是否与项目自身许可证兼容
- 归因层：`THIRD_PARTY_NOTICES` / `NOTICE` / 依赖许可证全文是否齐全
- 声明层：源文件是否有版权头 / SPDX 标识 / AI 使用声明

三层缺一层，"原创"就只能靠嘴说，无法在审计或客户尽调时自证。

### D2 PII 检测只输出掩码与位置

```
invariant: 报告、JSON、SARIF、缓存中不得出现原始 PII 值
contract:  复用 Finding；evidence 走 mask()，detail 只放类型与计数
test:      序列化后的报告全文不得包含测试样本里的原始值
```

这是本工具自身的合规底线：帮别人找 PII 的工具，自己不能变成 PII 泄漏源。扫描结果不联网、不写缓存原文。

### D3 许可证组合冲突独立成规则

```
contract: project license × dependency license → 冲突矩阵
invariant: 确定的冲突报高危；未知组合报提示并附判据，不猜
test:      MIT×GPL-3.0（冲突）、Apache-2.0×GPL-2.0（冲突）、MIT×MIT（通过）
```

现状只逐条报"某依赖是 GPL"，用户无法判断"我的 MIT 项目能不能用"。组合判定才是原创性问题的真正答案。

### D4 辖区决定 PII 规则集

```
decided:   东南亚五国全选（sg-pdpa / th-pdpa / id-pdp / my-pdpa / ph-dpa），写入 .pdp-compliance.json
invariant: 未配置辖区时只跑通用格式（邮箱/手机号/银行卡），不报辖区证件号，报告标注"未按辖区校验"
```

通用格式：邮箱、手机号、银行卡（Luhn）、身份证号粗匹配。辖区规则（SG NRIC、TH 身份证、ID NIK、MY MyKad、PH PhilSys）按需加载。

## 能力矩阵

| 能力 | 现状 | 缺口 | 归属 |
| --- | --- | --- | --- |
| 依赖漏洞 | 已有（OSV） | — | 风险 |
| 依赖许可证 | 逐条判定 | 项目许可证 × 依赖组合 | 原创性 |
| 凭据泄漏 | 已有（含 base64、去重） | — | 风险 |
| PII / 敏感数据 | 无 | 新增 | 风险 + 合规 |
| 供应链 | 已有（仿冒、浮动版本、CI 权限） | — | 风险 |
| AI 代码风险 | 已有（幻觉依赖、危险调用） | AI 使用声明 | 原创性 |
| 归因完整性 | 无 | NOTICES 生成与缺失检查 | 原创性 |
| 来源可证明 | 半（SBOM 对账） | vendored 代码来源记录 | 原创性 |

## 优先级

| 级别 | 能力 | 理由 |
| --- | --- | --- |
| P0 | PII 检测（通用 + 辖区可配） | 唯一完全缺失的维度，且是"风险"与"合规"的交汇点 |
| P0 | 许可证组合冲突 | 成本低、直接回答"我的项目能不能用这个依赖" |
| P1 | 归因完整性（NOTICES 生成与检查） | 让"原创"从声明变成可提交的证据 |
| P2 | AI 使用声明 + vendored 来源记录 | AI 时代原创性的长期答案，但需要约定格式 |

## 验收

```
test: 每个新增能力至少 3 个质量用例（真阳性 / 真阴性 / 边界）
test: PII 掩码不变量——序列化输出不含原始值
test: 组合矩阵覆盖三组典型许可证搭配
test: --skip pii 可整体关闭，测试数据不产生噪音
```

## 实施记录（0.4）

### P0-1 敏感数据扫描 —— 已完成

- 6 条规则：`PII-001` 邮箱 / `PII-002` 手机号 / `PII-003` 政府证件号 / `PII-004` 银行卡 /
  `PII-005` 疑似数据快照 / `PII-006` 日志打印 PII
- 辖区由 `.pdp-compliance.json` 驱动（五国全选）；未声明时只跑通用格式，不报证件号
- 隐私不变量已落地：只存掩码与位置，报告/JSON/SARIF/缓存无原始值，有测试断言
- 证件号优先于卡号判定（16 位 NIK 可能通过 Luhn，不能误判）
- 测试目录命中降级为置信度 ≤ 0.4，不参与门禁

### P0-2 许可证组合矩阵 —— 已完成

- 新增 `provemark/rules/license_compat.py`：11 个兼容类、`ok / conditional / incompatible / unknown`
- `LIC-009` 报确定冲突（高危，dev 中危）；`LIC-010` 按组合聚合无法判定的情形（提示，最多 5 组）
- `LIC-004` 与组合判定分离：策略禁止但组合兼容时降为提示（GPL 项目用 GPL 依赖不再误判高危）
- `conditional` 不产出 finding（弱传染保留声明即可用），`WITH` 例外不建模、归为 `unknown`
- 矩阵遍历覆盖策略放行的依赖——这是原实现的盲区（Apache-2.0 依赖进入 GPL-2.0 项目会被直接跳过）

### 质量基准

- 17 个带标注用例，precision 1.00 / recall 1.00
- 许可证组合新增 1 个离线用例：通过预置许可证缓存，让 `--offline` 也能复现 `LIC-009`

### P1 归因完整性 —— 已完成

- `provemark notices`：运行时依赖 → `THIRD_PARTY_NOTICES.md`，未知许可证单独列出
- `HYG-014`（缺归因文件）/ `HYG-015`（归因漏包）
- `--offline` 改为"只读缓存"的许可证解析，离线也能给出结论

### P2 AI 使用声明与 vendored 来源 —— 已完成

- `provemark ai-usage` + `AI-013` / `AI-014`：只根据助手配置文件推断"用过 AI"，不猜测生成内容
- `provemark vendored` + `SCP-014` / `SCP-015`：复用 FOSSA 的 vendored 目录识别，
  排除 `node_modules` 等包管理器目录；上游与 Commit 留 TODO，不伪造来源
- 两处都遵循「不覆盖手写文件、未知就标注」的原则

### 仍在待办

- 无新增 P0/P1；后续按使用反馈调整规则阈值（尤其 `SCP-014` 在 monorepo 中的噪音）

## Working notes

- 不做代码相似度查重（误报高、结论不可操作）
- PIPL / GDPR 不在当前合规参考覆盖范围；若要支持需单独维护规则集，不能假装覆盖
- `.pdp-compliance.json` 是否落地，取决于辖区选择
- 候选实现顺序：PII → 组合矩阵 → NOTICES → AI 声明
